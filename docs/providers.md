# Provider adapters and capability gates

Provider adapters run server-side. Secrets, raw AI prompts and private billing data stay out of browser configuration and general exports. Provider HTTP performs an allowlisted HTTPS request, rejects credentials/custom ports/redirects/compression, resolves public DNS addresses and pins the chosen address, enforces response-byte/time limits, and validates response schemas. RSS hosts must be operator approved.

Availability describes configured prerequisites and always reports `liveVerified: false`. Presence of a key is not evidence that the provider accepted a request, the operator account is eligible, or music playback exists. The normal API can start without optional provider credentials.

## Social sources and external events

Social source configuration is tenant owned. First polling records a baseline without announcing existing items unless the manager explicitly selected that behavior. Repeated source event IDs cannot create another announcement. Poll and event budgets are persisted per UTC day. An event beyond the daily announcement budget is explicitly recorded as skipped; it is not silently replayed later. Disabling/changing a source invalidates a previously prepared poll result by revision.

Webhook provisioning returns a tenant-specific `/api/v1/provider-events/:guildId/:integrationId` endpoint and stores the encrypted signing key separately. Send `application/json` with `x-sparko-timestamp` as Unix seconds and `x-sparko-signature` as hexadecimal HMAC-SHA256 over `timestamp + "." + exact raw bytes`. The JSON timestamp must match the signed header. Verification happens before the mutation transaction; the transaction rechecks module/integration state, allowed event types and age. A repeated event returns its original receipt; changed content under an existing event ID conflicts. Revocation removes the signing key. Event links require HTTPS without embedded credentials.

## AI disclosure, authority and ambiguous attempts

AI requires both manager opt-in for the purpose/external sharing and per-request member consent. Ticket summaries additionally require current own-ticket or `tickets.manage` authority and a complete retained transcript. The request stores the exact transcript identity/checksum; worker preparation rechecks the request owner's fresh authority, current purpose consent/limits and retained ticket material.

The domain reserves conservative input/output usage before dispatch. The worker changes `pending` to `generating` before a billable call, using a distinct dispatch attempt identity. A subsequent attempt cannot dispatch again after an ambiguous provider failure. Raw prompts are read privately after reservation and never included in operation receipts/outbox payloads. Completion removes the stored prompt and marks the text as requiring human review; AI cannot perform actions. Retention deletes expired requests. A generating/unknown request needs operator reconciliation instead of an automatic second charged call.

## Billing scope and ordering

Checkout is tied to a guild and manager-authorized intent; the provider idempotency key comes from that intent. A browser success URL grants no access. When all four PayPal settings are present, checkout uses PayPal; otherwise it uses Stripe. A manager picks a billing period among the PayPal plans configured (monthly, every 6 months, yearly); each is the same Plus plan, and a subscription on any other plan is refused. `/api/v1/webhooks/paypal` asks PayPal's verify-webhook-signature API to check the exact received bytes against `PAYPAL_WEBHOOK_ID`, refuses transmissions older than 30 minutes, then reads the subscription from PayPal (following a sale or dispute to its subscription) before applying it through the same `recordEntitlement` rules as Stripe. A cancelled PayPal subscription keeps Plus until the end of the paid period (the last next-billing time plus one day of grace); suspension, expiry, refunds, reversals and open disputes end it. `/api/v1/webhooks/stripe` verifies the exact raw-body Stripe signature and retrieves the current subscription outside the database transaction before applying it. An entitlement requires matching guild/user intent and the configured recognized price. Billing amounts/currencies are stored separately from virtual currency.

Duplicate callback IDs are idempotent and changed payloads conflict. The latest retrieved subscription observation controls current status/period data. Refund/chargeback hold chronology is tracked separately: an older dispute closure cannot clear a newer hold, and a delayed refund revokes the current entitlement even if its subscription fetch completed earlier. Canceled/past-due/expired/revoked state has no effective paid entitlement. Scheduled expiry ignores superseded observations. Account/region availability, real sandbox checkout/callbacks and operator refund/dispute policy still require verification.

## Plans, limits and staff grants

Plan limits live in `plans` (`packages/domain/src/core.ts`) and are enforced by `requirePlanRoom` and `featureGate`; see `docs/milestones/m6.md` for the table. The effective plan is Plus while any provider-verified or staff-granted `billing.entitlement` is active, unrevoked and unexpired; expiry is read from the instant, so a missed expiry job cannot extend access. Staff grants (`entitlements.manage`) record a reason, expire on their own and can be revoked; provider subscriptions are never edited by staff. Losing Plus keeps every record and setting; only new work past a Free limit is refused.

## Verification and exact live checks

Pure tests exercise byte-sensitive signatures, stale/forged callbacks, ciphertext corruption, unsafe URLs/addresses, RSS entity rejection, all selected social adapter protocols, checkout idempotency/URL safety, current subscription retrieval, AI human review/storage policy, and authorize-all-before-read multi-server behavior. PostgreSQL tests exercise webhook replay/tenant/age/revocation rules, baseline/dedupe/budgets, concurrent AI quota/dispatch and private output, consent rechecks/retention, unavailable music, and billing duplicate/out-of-order/hold/expiry/scope transitions.

Adapter protocol fixtures are local tests, not provider sandbox verification. Remaining live checks are an operator-approved RSS source; public release/video/live-stream polling with valid credentials and quotas; OpenAI generation/cost/retention; Stripe supported operator account and signed sandbox checkout, failure, cancellation, refund/dispute and reconciliation events; and an actual permitted-source voice runtime with queue/skip/volume/idle cleanup. Provider credentials are configured through the approved environment flow, never pasted into chat or committed.
