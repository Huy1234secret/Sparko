# M5 — Time and automation workspaces

Complete locally. Delivered through the M5 milestone PR (see progress.md for the PR and CI run). Live Discord acceptance remains an external prerequisite.

The M5 backend (timers, Gateway ingestion, worker effects) was already in place; see `docs/safety-automation.md`. M5 replaces the generic module pages for these features with typed workspaces on the shared design system. It also adds member-side controls to the member profile. No page asks staff to write JSON.

## Delivered behavior

**Shared building blocks** (`apps/web/src/features/automation`)

- Times are edited as wall-clock times in a chosen IANA time zone (default: the browser's). Every displayed time names its zone.
- Daylight-saving rules match the server: a repeated local time uses its first instant, and a skipped one moves forward to the first minute that exists.
- Repeats are "don't repeat", "every day" or "every week". The repeat keeps the first occurrence's local weekday and time, so there are no separate hour and weekday fields to get out of step.
- Each page has an on/off settings tab, a notice when the module is off, and plain-language state badges.

**R33 polls**

- Typed choices are added and removed one at a time. Duplicate choices are refused, and members cannot pick more choices than exist.
- Settings for: who sees results, whether members can change their vote, required roles, and an optional Discord post.
- Results are shown as bars with vote counts. Staff can close voting early.
- Members vote from their profile (one choice or several). A vote that cannot be changed says so.
- The page says polls are not anonymous to managers.

**R37 events and RSVP**

- Start and end are set in the event's time zone. Other settings: places, required roles, the reminder lead time and an optional announcement.
- Scheduled events can be edited. Cancelling requires a reason, which everyone going or waiting receives.
- Members RSVP from their profile. A full event offers its waitlist, and members can leave the event or its waitlist.

**R66 reminders**

- Members set personal direct-message reminders from their profile.
- Staff with automation access can also send to a channel.
- A reminder can repeat and has a misfire choice. If Sparko was offline, the reminder list shows that the last one was skipped.

**R38 birthdays**

- Staff settings: the announcement channel, the local hour, an optional birthday role (only roles Sparko can grant) and how long the role lasts.
- Members add, change or remove their own birthday, choosing who knows and what happens on 29 February. The year is never collected.

**R39 temporary voice**

- Settings: the lobby voice channel, the room category, the name template, the default limit and the cleanup delay.
- Staff see active rooms.
- Owners rename their room, set its limit, lock or unlock it, let members in, remove their access, transfer ownership or delete it (with confirmation). They can do this from the page or from their member profile, where the card appears only while they own a room.

**R40/R41 invite tracking and rewards**

- Confirmed, ambiguous and unknown joins are counted separately, with the reason for each. An uncertain join never names an inviter.
- Reward settings: the role, minimum stay, account age and reversal when the member leaves. Rewards given are listed.
- New staff route: `GET /invite-rewards` (`analytics.read`).

**R42 scheduled messages**

- Post a public Message Studio design, previewed, once or on a repeat, in a chosen zone, with a misfire policy.
- The list shows the next post and skipped occurrences. Schedules can be cancelled.

**R43 auto replies**

- Settings: the match type, the words, the reply, a per-channel cooldown, the channels it applies in and excluded roles.
- A "Try a message" panel uses the same matching function as the bot. That function, `replyMatches`, moved into `@sparko/contracts`, and Gateway ingestion now calls it.

**R44 sticky messages**

- One sticky message per channel, built from a public design, with a quiet period before reposting. The list shows the last repost error.
- The channel is fixed; to move a sticky message, turn it off and create a new one.

**R45 workflows**

- A step builder with a typed form for each step type:
  - send a message
  - give or remove a role (only roles Sparko can grant)
  - open a ticket (chosen from the ticket types)
  - wait (amount and unit)
  - check a role (later step targets only)
- Steps can be moved and removed. Role-check targets follow the steps they pointed at.
- A dry run traces the path for a chosen set of roles with the engine's rules. Waits and role checks are free, and other steps spend the action limit. It shows where a run would stop.
- Staff run a workflow for themselves. The Runs tab shows each run's progress, waits, errors and action count, and running runs can be stopped.

**R46 custom commands**

- The name is typed after a fixed `/spark-` prefix. Only active workflows can be chosen.
- Settings for role limits and the description, plus the registration state ("Registering with Discord" or "Ready in Discord").
- The page states that commands only start workflows.

## Evidence

Local run on Node 24.19.0, with disposable PostgreSQL 16 and Redis 7 (CI uses PostgreSQL 17.6 and Redis 7.4.6):

- typecheck, lint, format and build pass, including the prerender and browser-boundary checks.
- **251** unit tests, **154** PostgreSQL integration tests and **19** browser journeys pass.

New focused coverage:

**Unit**

- Time-zone conversion both ways.
- A daylight-saving gap and repeat in New York.
- Repeat derivation.
- The workflow dry run: branches, budget stop, and move/remove retargeting.
- Shared reply matching (case and full-width characters).

**Web**

- Building a poll, with duplicate-choice refusal and the exact request body.
- Poll results and closing.
- A member's single and final votes.
- The waitlist RSVP.
- A member's weekly reminder (direct message only).
- Cancelling an event with a reason.
- The workflow builder: typed steps, the dry run, retargeting after a move, and the saved body with no JSON.
- The reply tester.
- Command prefixing and active-workflow filtering.
- Invite certainty display.

**PostgreSQL**

- Invite rewards are visible only to analytics readers and only for their own server.
- Auto replies match through the shared rule; a non-matching message sends nothing.

**Browser journeys** (`tests/e2e/automation.spec.ts`)

- A poll is created and voted on from the member profile. Staff see the voter and close it, and it disappears from the member's open polls.
- A workflow is built from typed steps (send, then wait one minute) and its dry run checked. Run once, the real worker posts exactly one message; the run then waits and is stopped.
- A member sets a daily reminder from their profile and cancels it.

As in earlier milestones, only Discord's external boundary is controlled. The API, database, worker and BotRuntime are the real code.

## Setup

No migration or environment changes.

- Invite tracking needs Sparko to have the Manage Server permission to read invites.
- Auto replies need the Message Content intent.
- Temporary voice needs Manage Channels and Move Members.

## Manual smoke

1. Turn on polls. Create a poll with three choices that closes in 10 minutes and posts in a test channel. Vote in Discord and from the member profile, then check the results.
2. Turn on events. Create an event with 1 place. RSVP with two accounts, confirm one is on the waitlist, then have the first decline and confirm the second gets the place and a DM.
3. Turn on workflows. Build "give role, wait 1 minute, send message", run it for yourself, and watch the Runs tab.
4. Create `/spark-hello` for that workflow and use it in Discord.
5. Turn on temporary voice with a lobby channel. Join the lobby, rename the room from the member profile, leave it, and confirm cleanup.

## Remaining boundaries

The following still need a live Discord application and test guild:

- Gateway message, join, leave and voice events.
- Invite observations.
- Command registration.
- DMs.
- Role grants.

A waitlisted member is promoted in queue order. Their roles are not checked again at promotion, because only their roles at RSVP time are known (fresh waitlist eligibility).

Ambiguous voice-room creation still needs reconciliation.

Staff and member lists show Discord user IDs, not display names.
