# Backend

The backend is being rebuilt in stages on top of the new dashboard. Everything runs in two pm2 processes and one database file; there's no Docker, Postgres or Redis.

| Part     | Where           | What it does                                                                                        |
| -------- | --------------- | --------------------------------------------------------------------------------------------------- |
| Database | `packages/core` | One SQLite file (Node's built-in `node:sqlite`), shared by both processes. Migrations run on start. |
| API      | `apps/server`   | Discord sign-in, the dashboard's `/api/v1/…` routes, and the website itself.                        |
| Bot      | `apps/bot`      | Discord gateway: keeps the server list current, reports its latency, applies saved changes.         |

## How a saved change reaches Discord

1. The dashboard saves (for example `PUT /api/v1/servers/:id/modules/levels`).
2. The API stores the setting and a version, writes the activity log, and adds a **job**.
3. The bot checks for jobs every second, applies each one in Discord, and marks it done or records what went wrong in plain words.
4. The dashboard waits on `GET …/modules/:id/apply` and shows Live or the problem. If the bot is offline it says the change is saved and applies when the bot is back.

Modules without their own settings page yet can be switched on and off; what they do in Discord is built as each area's pages are.

## Data and backups

- The file is `.data/sparko.db` in the app folder (or `DATABASE_PATH`). It's ignored by git, so updates keep it.
- Back it up with `sqlite3 /opt/sparko/app/.data/sparko.db ".backup /opt/sparko/shared/sparko-backup.db"`, or stop both processes and copy the file.
- Sign-ins are stored hashed, with the Discord access token encrypted using the app's client secret. Changing the secret signs everyone out.

## Welcome

- The dashboard reads and saves Welcome at `/api/v1/servers/:id/welcome`; settings are checked (delivery, channel, lengths, colour) and only known fields are stored.
- After a save the bot checks it can post in the chosen channel and explains what's missing if not. "Check again" re-queues the change (`POST …/modules/welcome/apply`).
- When someone joins, the bot sends the message with `{user}`, `{server}` and `{member_count}` filled in. Only the new member can be pinged. With "Welcome people who rejoin" off, people who joined before aren't greeted again.
- Discord only tells bots about new members with the **Server Members Intent** on (Developer Portal → your app → Bot → Privileged Gateway Intents). Without it the bot still runs, and saving Welcome says what to turn on.

## Tickets

- Saving Tickets (`PUT /api/v1/servers/:id/tickets`) checks the panel (channel, title, 1–5 buttons, staff role ids, auto-close) and queues a job; the bot posts the panel with its buttons, edits it in place on later saves, posts it again if someone deleted it, and removes it when Tickets is turned off.
- Pressing a button opens a private thread (`ticket-N`), adds the member, and posts the opener with the button's question, pinging the staff roles if that's on. With "one open ticket per member", a second press points to the open one.
- Messages typed in the thread are kept in the inbox (the member's first message becomes the ticket's subject). Staff can also reply from the dashboard (posted by Sparko as "**Name:** text"); staff notes stay in Sparko.
- Assigning, priority, closing (locks and archives the thread, optionally tells the member by DM), reopening and the HTML transcript all work from the dashboard. Tickets whose member stopped replying are warned two hours before the auto-close time and then closed.
- Staff with Discord's Manage Threads permission see every ticket thread; with "ping these roles" on, the roles are also mentioned (and added) in each new ticket.
- Ticket messages typed in Discord need the **Message Content Intent** (Developer Portal → Bot). Without it the inbox shows that Discord didn't share the text.

## Message Studio

- Two layouts: the **classic** message (text, one embed, link buttons) and **Components V2** (blocks: text with headings, text with an image or button beside it, image galleries, separators and link-button rows, optionally in a box with a coloured bar).
- Both are edited in the live preview: click text to change it in place; in Components V2, hover a block to move or remove it and use + to add blocks. Links and options for the selected block are in the side panel.
- Publishing (`PUT /api/v1/servers/:id/studio`) checks the message the way Discord would (lengths, https links, 6,000-character embeds, 4,000 characters of V2 text, 1–10 gallery images, up to 5 buttons) and queues a job. The bot posts it, then edits the same message on later publishes. Discord can't switch a posted message between layouts, so switching layout posts a new message.
- Edit message (`POST /api/v1/servers/:id/studio/edit` with `{ message, link }`) turns a message Sparko already sent into the template, given its Discord message link. The link must be for this server; the bot edits the message in place (it keeps its link) and its buttons and menus then do what the template's do. Discord only lets a bot edit its own messages, and a message can't switch between the classic and V2 layouts.
- Mentions are shown but never ping anyone (`allowed_mentions` is empty).
- Templates (`/studio/templates`) are saved per server, up to 100 on Free and 500 on Plus, and can be sorted into folders (`/studio/folders`), 20 on Free and 100 on Plus. Folders can hold folders.
- Templates and folders share one order inside each folder. `POST /studio/library/move` with `{ kind, id, folderId, index }` puts an item at `index` among the other items in `folderId` (`null` is the top level); a folder can't move inside itself.
- `POST /studio/templates/:id/clone` puts the copy right after the original. Deleting a folder deletes everything in it and answers with how many templates and folders went.
- A message holds up to 10 embeds; their text adds up to Discord's 6,000-character limit. Messages saved before this are read as one embed.
- `POST /studio/test` posts the message as a new message in its channel and keeps it as a version.
- `POST /studio/uploads` takes a PNG, JPEG, GIF or WebP picture of up to 5 MB as the request body and answers with a public link. The bytes decide the type. Files are kept in `MEDIA_DIR` (default: a `media` folder next to the database) and served at `/media/<name>` so Discord can load them.
- `GET /studio/emojis` lists the server's own emojis for the emoji picker.
- Messages have `components`: buttons and menus, laid out as Discord does (up to five buttons in a row, each menu on its own row, at most five rows). Older messages' link buttons are read as link buttons.
- An action button or a menu option runs its actions from top to bottom: **Send message** sends templates (in the channel, in the clicker's DMs, or as a reply only they see) and **Give or take role** changes the clicker's roles. Free servers send 1 template per action, Plus up to 10; the server refuses more.
- Every Studio message the bot posts that has buttons or menus is kept in `studio_posts`, so the bot can find what a click should do. Buttons and menus use custom ids `sp:b:<id>` and `sp:m:<id>`. The bot acknowledges each click straight away and tells the clicker privately if something didn't work, such as a role above Sparko's.
- Components V2 messages are one container: a colour bar, text (`{separator}` becomes a divider), a thumbnail beside the first stretch of text, and an image gallery of up to 10 pictures. `v2.place` says where each button, menu and the gallery sits: after a line of the text (`line: -1` is the top of the container), beside a line (buttons only; Discord shows it as a section with the button on it), or above or below the container. Messages saved with the older part order, or as separate blocks, are read into this shape.
- Text can hold variables in braces: `{user}`, `{user.name}`, `{user.id}`, `{server}`, `{server.members}`, `{channel}`, `{date}` and `{time}` (Discord timestamps, shown in each reader's own format). Sparko fills them when it sends: from the staff member who posted, or from the member who clicked a button. A variable with nothing to fill it is left as written.
- Every post is kept as a version.

## Suggestions

- Settings are saved at `/api/v1/servers/:id/suggestions` (`GET`, `PUT`). The check (`sgIssue` in `packages/core/src/suggestions.ts`) is shared by the dashboard, the API and the bot: channels, role lists, the account age (1d to 1y), auto-close (1mi to 1mt), the cooldown (1h to 1mt), statuses (6 on Free, 20 on Plus, names up to 25 characters, up to 5 actions each), auto-approve and auto-deny (0 to 10,000), lengths (up to 12,000) and the commands' names. Times are written with `mi`, `h`, `d`, `w`, `mt` (30 days) and `y`.
- The message is a Message Studio template (tagged **Suggestion** in Studio) with one embed or container, no pictures and no buttons or menus of its own; with no template picked Sparko uses its Suggestion card. Variables: `{user.suggestion}`, `{suggestion.title}`, `{suggestion.id}`, `{status}`, `{vote.ratio.amount}` (`` `100 | 120 - -20` ``), `{vote.ratio.percent}` (`` `35% | 65% - -15%` ``, adding up to 100), `{upvotes}`, `{downvotes}` and `{files}`. Pictures and videos people attach show in the message. A suggestion too long for one message carries on in more messages, each one embed or container.
- Saving queues a `suggestions` job: the bot checks it can post (and react, and open threads, where that's on) in the channels, and registers the server's own commands with the names picked in Commands (`PUT /applications/:app/guilds/:guild/commands`). Turning Suggestions off removes them.
- `/suggest` opens a form (a title, then one to three boxes for the text, as the longest length needs) and takes up to 3 files. Who can suggest, the blacklisted role, the account age (which the suggest roles can bypass), the cooldown, the pending limit, the lengths, duplicates and the storage limit are checked when it's sent; a refusal is only shown to the member and is logged.
- With a review channel, new suggestions go there first with **Post it** and **Reject** for staff who can approve. Rejecting asks for a reason and never posts it.
- Votes are reactions, buttons (`sg:up`, `sg:down`) or a menu (`sg:vote`), kept in `sg_votes`. Changing votes, voting on your own suggestion, auto-approve and auto-deny follow the settings; refused reactions are taken off. Message edits after votes are batched so a busy suggestion doesn't hit Discord's limits.
- `/suggestion-status`, `/suggestion-approve` and `/suggestion-deny` ask for a reason, then set the status, run its actions in order (approve, deny, close voting, DM the author with a template or Sparko's own message, give the blacklisted role) and add a box under the suggestion with who set it and why.
- If someone deletes a suggestion in Discord, the audit log says who (Sparko needs View Audit Log). Someone with a delete role (or Manage Server when none are picked) deletes it for good; anyone else, and Sparko posts it again with its votes and data.
- Auto-close is checked every minute. Closing greys out the vote buttons and locks the suggestion's thread.
- Storage: `GET …/suggestions/list?q=&status=` lists suggestions newest first; `DELETE …/suggestions/:number` removes one straight away and the bot takes its messages down. Each suggestion counts 4 KB of the server's storage (10 MB on Free, 100 MB on Plus).
- `POST …/suggestions/test` with `{ channel }` posts a made-up suggestion there with the saved message.

## Reaction roles: Sparko's template

The claim and remove messages can be **Sparko's template** (`sparko`) instead of a Studio template: "Added {role.selected.list}" and "Removed {role.removed.list}". It isn't one of the server's templates, so it doesn't count toward them, and the dashboard shows it without letting it be edited. `{role.selected.list}` and `{role.removed.list}` work in any response.

## Polls

- Settings are saved at `/api/v1/servers/:id/polls` (`GET`, `PUT`). The check (`pollsIssue` in `packages/core/src/polls.ts`) is shared by the dashboard, the API and the bot: the default channel, who can make polls (roles; none means Manage Server), whether members can make them with the command (and an optional role), what new polls start with (buttons or a menu, anonymous, multiple choice, changing votes, hidden results, a default length of 1mi to 1mt), the role to ping, the two templates and the command names. The command name can't be one Suggestions already uses.
- A poll has 2 options up to 5 on Free and 25 on Plus, each with a name (up to 80 characters) and an optional emoji, and Free runs 3 polls at once (posted or scheduled), Plus 50. Each poll sets its own rules: buttons (five to a row) or a menu, anonymous, multiple choice with the most picks (0 for any), changing votes, hidden results, the roles that can vote, a role to ping once when it's posted, ending never, after a while (1mi to 30d, counted from posting) or at a time (up to 60 days), and ending after a number of voters. `pollDraftIssue` checks a new poll everywhere.
- The poll and its results are Message Studio templates (tagged **Poll** in Studio; Sparko's Poll card and Results card when none is picked). The option buttons (`pl:v:<option>`) or menu (`pl:m`) are added under the message; a classic message's own buttons share Discord's 5 rows with them. Variables: `{poll.question}`, `{poll.options}` (each option with `▰▰▰▰▰▰▱▱▱▱ 60% (12)`, or just the options while results are hidden), `{poll.id}`, `{votes.total}` (members who voted), `{poll.ends}` (a relative time, or "No end time"), `{poll.author}`, `{poll.winner}` (the winner, a tie, or the option a reroll picked) and `{poll.status}`.
- Polls are kept in `polls`, votes in `poll_votes` (one row per pick, with the member's name for the voters list) and what happened in `poll_log` (made, posted, ended and why, rerolled, deleted, failed). A deleted poll's number isn't used again.
- The dashboard makes changes in Discord through jobs the bot runs: `POST …/polls` with `{ draft }` saves a poll and queues `polls-post` (one for later waits for the minute sweep); `POST …/polls/:id/post` posts a scheduled one now; `POST …/polls/:id/end` and `POST …/polls/:id/reroll` (ended ties only) change it straight away and queue `polls-refresh` to edit the message; `DELETE …/polls/:id` forgets it and queues `polls-delete` to take the message down; `POST …/polls/test` with `{ channel, kind }` posts a made-up poll or results. `GET …/polls/list` lists polls (running, then scheduled, then ended) and `GET …/polls/:id/voters` who voted for what, never for anonymous polls. A poll Discord refuses is removed and logged.
- Saving queues a `polls` job: the bot registers the server's commands and checks it can post in the default channel. A server's own commands from every module are registered together (`apps/bot/src/guild-commands.ts`), since Discord replaces the whole list each time.
- `/poll create` opens a form (the question, the options one per line with an optional emoji first, and how long; empty uses the default, "never" for no end) and takes `anonymous`, `multiple` and `channel`. `/poll end`, `/poll results` and `/poll voters` take the poll's number, with suggestions as people type. Staff and whoever made a poll can end it. Results stay hidden from members until it ends; voters are never shown for anonymous polls. Every part can be renamed or turned off in Commands.
- A vote is answered privately ("You voted Pizza. Press again to take it back.") and the message is edited once per burst of votes. The minute sweep posts scheduled polls and ends ones past their time; reaching the vote target ends a poll at once. An ended poll shows the results template with the buttons greyed out and the winner in green.

## Starboard

- Settings are saved at `/api/v1/servers/:id/starboard` (`GET`, `PUT`). The check (`sbIssue` in `packages/core/src/starboard.ts`) is shared by the dashboard, the API and the bot: boards (1 on Free, 5 on Plus), each with a name up to 32 characters, its own channel, 1 to 5 star emojis, a threshold of 1 to 1,000 stars, the channels it watches or skips (up to 50), an age limit of 0 to 365 days, a shortest length of 0 to 2,000 characters, up to 25 blocked roles, and the staff roles and command names. Saving forgets the starred messages of boards that were removed.
- Each board posts with a Message Studio template (tagged **Starboard** in Studio), or Sparko's Classic starboard. Sparko adds a fixed **Jump to message** link button, so an embed post has up to 4 rows of its own. Variables: `{stars}`, `{star.emoji}`, `{board}`, `{author}`, `{author.name}`, `{author.avatar}`, `{jump.link}`, `{message.content}`, `{message.image}` (the first picture; like `{author.avatar}` it can be a picture link, and is left out when there's none) and `{message.date}`. `{user…}` is the author too, and `{channel}` is where they wrote it. Without the Message Content Intent the text shows as "Discord didn't share the text of this message".
- The bot listens to reactions being added, removed, cleared and cleared for one emoji, and to deleted messages. Stars are kept per board in `sb_reactors` (one row per member, emoji and place), so a member who uses two of a board's emojis, or stars both the message and its board post, counts once. The rules (the author's own star, bots' stars, bots' messages, watched channels and their threads, NSFW channels unless the board's is too, age, length, blocked roles, blocked members and messages) are checked in `sbSkipReason` and `sbStarCounts`. A message Sparko first sees with more stars than it saw being added is recounted from Discord (`GET …/reactions/:emoji`, up to 1,000 per emoji).
- `sbSync` makes a board match its stars: it posts a message that reached the threshold, edits the count on a post, and takes a post down when it drops below the threshold if the board says so. The bot runs it at most once per post every 2 seconds. Milestones at 10, 25, 50 and 100 stars are logged. When the original is deleted, each board keeps the post (frozen) or takes it down; a board post deleted by hand leaves the board.
- `/starboard top [board] [member]`, `/starboard random [board]`, `/starboard stats [member]`, and for staff (the staff roles, or Manage Messages) `/starboard freeze message` and `/starboard block [message] [member]`, which toggle. The command and its subcommands can be renamed, described or turned off in Commands. Suggestions and Starboard register the server's commands together (`apps/bot/src/guild-commands.ts`), since Discord replaces a server's whole list each time.
- Storage: `GET …/starboard/list?board=&sort=stars|newest&q=` lists starred messages; `POST …/starboard/entries/:board/:message/freeze` with `{ frozen }`; `DELETE …/starboard/entries/:board/:message` takes one off its board and forgets its stars; `POST …/starboard/blocked` with `{ kind: 'message', id, channelId }` or `{ kind: 'member', id, name }`, and `DELETE …/starboard/blocked/:kind/:id`. The bot takes posts down (`starboard-delete` jobs). Each starred message counts 2 KB of the server's storage (10 MB on Free, 100 MB on Plus); when it's full, new messages aren't posted and the log says so.
- `POST …/starboard/test` with `{ board, channel }` posts a made-up starred message there with the board's saved post.

## Birthdays

- Settings are saved at `/api/v1/servers/:id/birthdays` (`GET`, `PUT`). The check (`bdIssue` in `packages/core/src/birthdays.ts`) is shared by the dashboard, the API and the bot: the channel, the hour (0 to 23), the server's time zone (any IANA zone the system knows), the birthday role (Sparko has to be able to give it), who can manage birthdays, the account age (1d to 1y), the time in the server (1h to 1y), the time between changes (1d to 1y), the four message templates and the command names. A group name a turned-on suggestion command already uses is refused.
- The messages are Message Studio templates (tagged **Birthday** in Studio): **Birthday** (one member), **Several birthdays** (everyone at once), **This month** and the **DM**. With none picked Sparko uses its own. Variables: `{birthday.users}` (mentions, "<@1>, <@2> and <@3>"), `{birthday.count}`, `{birthday.age}` (one birthday, when the year is saved and ages are shown), `{birthday.date}` ("14 March"), and for the monthly post `{month}` and `{birthday.list}` (one "@member — date" per line). Mentions ping only the members it's for, and only with "Ping the birthday members" on; the monthly post never pings.
- Saving queues a `birthdays` job: the bot registers the server's commands and checks it can post in the channel and give the role. Per-server commands from every module are registered together (`apps/bot/src/guild-commands.ts`), because Discord's `PUT /applications/:app/guilds/:guild/commands` replaces the whole list.
- `/birthday set` (day, month, optional year and time zone with suggestions as people type, and a member for staff), `/birthday remove`, `/birthday view`, `/birthday upcoming` (next 10) and `/birthday list` (a month). The group and each subcommand can be renamed, described or turned off. Members' own changes check the account age, the time in the server and the time between changes (a new time zone alone isn't a change); staff (Manage Server, or the roles in Who can manage birthdays) skip them. Years give ages of 13 to 120; 29 February needs a leap year when a year is given.
- The bot sweeps every minute (`bdSweep`): a birthday is due on its day, at or after the hour, in the server's time zone or, with "each member's own", in the member's saved zone. 29 February is celebrated on 28 February in other years. The year is marked in `birthdays.celebrated_year` before posting, so a birthday is never posted twice; if Discord fails for a moment the mark comes off to try again, but a refusal (no permission, no channel) is logged and not retried. Everyone due in the same sweep shares one post, or gets one each. The birthday role is given for 24 hours (`role_until`) and taken back by the sweep, even after the module is turned off; if Sparko can't take it back for a day it gives up and logs it. The monthly post goes out on the 1st at the hour in the server's time zone, once (`bd_state.monthly`).
- Members who leave are hidden (never celebrated; left out of lists and the monthly post while "Hide birthdays of members who left" is on), or deleted with "Forget members who leave". Rejoining brings a hidden birthday back.
- Storage: `GET …/birthdays/list?q=` lists birthdays in calendar order with the next 10 (`upcoming`); `GET …/birthdays/members?q=` finds server members by name or ID (Discord's member search); `PUT …/birthdays/members/:userId` with `{ day, month, year, timeZone }` adds or changes one as staff; `DELETE …/birthdays/members/:userId` removes one and queues `birthdays-role-off` if they have the role today. `POST …/birthdays/test` with `{ channel, kind }` posts a made-up birthday message with the saved template.
- Logs (`bd_log`, the last 500): set, changed, removed, celebrated, role given, role removed, monthly post, and failures.

## Questions & answers

- Settings are saved at `/api/v1/servers/:id/questions` (`GET`, `PUT`). The check (`qaIssue` in `packages/core/src/questions.ts`) is shared by the dashboard, the API and the bot: the questions channel, who can ask, the blacklist and ping roles, who can answer (empty means Manage Server), the details' lengths (up to 2,000), the cooldown (1mi to 1mt), open questions per member (1 to 3 on Free, up to 20 on Plus), categories (5 on Free, 25 on Plus, names up to 30 characters with an optional emoji), the thread's auto-archive (1 hour, 1 day, 3 days or 1 week), what happens after an answer (close now, close after 1mi to 1mt, or keep open), expiring unanswered questions (1h to 1y) and the command names. A command name another module already uses is refused.
- Three Message Studio templates (tagged **Q&A** in Studio): the question message and the answer message, each one embed or container without pictures, and the DM sent when a question is answered. With none picked Sparko uses its Question card, Answer card and its own DM. Variables: `{question.title}`, `{question.body}`, `{question.id}`, `{question.category}`, `{status}` (Open, Answered, Closed, Expired), `{answer}` (the first 1,000 characters on the question; all of it in the thread and the DM), `{answered.by}`, `{answered.by.name}`, `{asker}` (and `{user}`, both Anonymous when questions are), `{metoo.count}`, `{thread}` and `{files}`.
- Saving queues a `questions` job: the bot registers the server's commands and checks it can post, open and manage threads in the channel (and ping the role). Discord replaces a server's commands all at once, so `guildCommandBodies` in `packages/core/src/guild-commands.ts` gives every module's commands together (Suggestions and Questions & answers), and each module registers that whole list.
- One command, `/question`, with the parts `ask`, `answer`, `close`, `reopen` and `delete`, each renamable and able to be turned off. `ask` takes a category (autocompleted) and up to 3 files, and opens a form with a title and the details. Who can ask, the blacklist, the cooldown and the open limit are checked before the form opens and again when it's sent; refusals are logged. The staff parts autocomplete question numbers and titles.
- Sparko posts the question with a public thread (`#12 Title`) and adds the asker to it unless questions are anonymous. Under it are fixed buttons: **Answer** (`qa:answer`, staff; opens a form with the earlier answer), **Mark answered** (`qa:done`, the asker or staff) and, when on, **Me too** (`qa:metoo`, kept in `qa_metoo`, edits batched).
- Answering posts the answer template in the thread (editing the earlier answer when staff answer again; the log keeps both), adds the answer under the question with who wrote it (unless the template shows `{answer}` itself), turns the question's colour to its status's, and DMs the asker when that's on. Mark answered closes it without an answer. The thread then closes as set: closing locks and archives it. `/question reopen` opens it again and clears the shown answer.
- Every minute the bot closes threads whose time is up and marks questions unanswered for too long as Expired. Deleting the question message in Discord marks it **Deleted in Discord** and locks its thread; staff still see it in Storage.
- Storage: `GET …/questions/list?q=&status=` lists questions newest first; `DELETE …/questions/:number` removes one and the bot takes its message and thread down. Each question counts 4 KB of the server's storage (10 MB on Free, 100 MB on Plus).
- `POST …/questions/test` with `{ channel, which }` posts a made-up question (without its buttons or ping) or answer there with the saved templates.

## Invite tracking

- Settings are saved at `/api/v1/servers/:id/invites` (`GET`, `PUT`). The check (`invIssue` in `packages/core/src/invites.ts`) is shared by the dashboard, the API and the bot: the fake account age (1h to 1y, or empty for none), the counting switches, the join and leave messages (a channel when on, and their templates), reward tiers (3 on Free, 25 on Plus; 1 to 100,000 invites, each count and each role once, roles Sparko can give), staff roles and the command names. A group name a turned-on suggestion command or the birthday command already uses is refused.
- Sparko needs **Manage Server** to read a server's invites. The bot asks for the **GuildInvites** intent (not privileged) and keeps each server's invites in `inv_codes`: read from `GET /guilds/:id/invites` on start, when it joins a server, after a save and on every join; added and removed on the gateway's invite create and delete events. The vanity link's uses come from `GET /guilds/:id/vanity-url` (`inv_state`).
- When someone joins, the bot reads the invites again and compares (`invDiff`): the one invite whose uses went up is theirs; a one-use invite Discord deleted as it was used up counts too (an invite deleted while one use from its limit is kept, as expired, until the next read). Otherwise, if the vanity link's uses went up it's a **vanity** join, and anything else (Discovery, several joins at once, no Manage Server) is **unknown**. Joins and leaves are handled one at a time per server so each read follows the last.
- Each join is a row in `inv_joins` (member, inviter, code, type, fake, counted, joined and left). An inviter's numbers: **regular** (counted joins), **left** (of those, members who left), **fake** (accounts younger than the fake account age; a fake who left is only taken off once) and **bonus** (`inv_people.bonus`). Total = regular − left − fake + bonus, with leaves and fakes taken off only when those settings are on. With "Count members who rejoin" off, a rejoin isn't counted again and the first inviter gets their invite back while the member is here.
- Reward roles (`invRewardPlan`) follow every change in a total (a join, a leave, a bonus, a reset, and after a save for everyone with invites): every tier earned, or only the highest, and with "Take rewards back" tiers dropped below come off.
- The join and leave messages are Message Studio templates (tagged **Invite** in Studio); with none picked Sparko uses its Join card and Leave card. Variables: `{inviter}` (a mention, "the vanity link" or "an unknown invite"), `{inviter.name}`, `{inviter.invites}` (the inviter's total after the change), `{invite.code}`, `{invite.uses}` and `{join.type}` (normal, vanity or unknown), with the usual `{user}` variables. They never ping.
- `/invites view`, `leaderboard [page]`, `who`, `list`, and for staff (Manage Server, or the roles in Who can manage invites) `bonus <member> <amount>` and `reset [member] [everyone]`. Discord needs a subcommand under a group, so the counts are `/invites view`. The group and each subcommand can be renamed, described or turned off; they're registered with every module's per-server commands.
- Storage: `GET …/invites/leaderboard?q=&page=` (25 a page; a search also finds members who only joined), `GET …/invites/members/:userId` (counts, who invited them, who they invited), `GET …/invites/find?q=` (server members, for a bonus), `POST …/invites/members/:userId/bonus` with `{ amount }`, `POST …/invites/members/:userId/reset` and `POST …/invites/reset` (resets stop invites counting and clear bonuses; who invited whom is kept; reward roles are updated by an `invites-rewards` job), `GET …/invites/codes` and `POST …/invites/test` with `{ channel, kind }`.
- Logs (`inv_log`, the last 500): joined (with the invite), left, reward given, reward removed, bonus, reset, and failures.

## Events & RSVP

- Settings are saved at `/api/v1/servers/:id/events` (`GET`, `PUT`). The check (`evIssue` in `packages/core/src/events.ts`) is shared by the dashboard, the API and the bot: the events channel, the time zone, who can manage events (`managers`, Manage Server when empty), the default reminders (each 1m to 30d before the start; Free 2, Plus 5), the default answers (Going is always on; Maybe and Can’t go can be turned off; names up to 30), the attendee list size (1 to 50), the attending role (Sparko has to be able to give it), Discord sync, which DMs are sent, the four message templates and the command names. A group name a suggestion command or the birthday command already uses is refused. `GET` also returns `upcoming`, `past`, the plan's `limits`, `canSync` (Sparko has Manage Events), text `channels`, `voice` (voice and stage channels, now part of `GuildView.voice`), roles and the log.
- Events: `GET …/events/items?when=upcoming|past`, `POST …/events/items` (create), `PUT …/events/items/:n` (edit), `POST …/events/items/:n/cancel`, `DELETE …/events/items/:n`, `GET …/events/items/:n/rsvps`, `PUT …/events/items/:n/rsvps/:userId` with `{ noShow }`, and `POST …/events/test` with `{ channel, kind }`. Each event is checked by `evEventIssue`: a title (up to 100), a description (up to 1,000), an https picture, a start in the future and up to 2 years ahead, a length of 5 minutes to 14 days, an IANA time zone, a voice or stage channel and/or a place in words (up to 100), a capacity (0 for none, up to 10,000), its answers, who can answer, a role to ping when posted, a repeat (none, daily, weekly, every 2 weeks, monthly), reminders within the plan, and an optional time to post before the start. Free servers have up to 5 upcoming events, Plus 100. The API saves the change and queues a job for Discord's side: `events-post`, `events-edit` (with who moved off the waitlist), `events-cancel` (with who was going) and `events-delete` (the message, Discord's event and roles to take back).
- The event message is a Message Studio template (tagged **Event** in Studio) with a fixed row under it: one button per answer with its count (`ev:rsvp:<n>:<choice>`; Going shows `n/capacity` and how many wait), and an **Add to calendar** Google Calendar link (kept within Discord's 512 characters). Once an event ends or is cancelled the buttons are disabled and an **Ended · 12 went** or **Cancelled** button replaces the calendar link. The event's picture is added to the embed or container. A message someone deleted is posted again on the next refresh. Answers reply privately; a burst of answers becomes one edit.
- Variables (`event: true`): `{event.title}`, `{event.description}`, `{event.id}` (#12), `{event.start}` and `{event.end}` (Discord full timestamps), `{event.start.relative}`, `{event.location}` (the voice channel and the place), `{event.host}`, `{event.link}` (the message's link, filled in right after posting), `{event.status}`, `{going.count}`, `{maybe.count}`, `{spots.left}` and `{going.list}` (the first names, “and 5 more”). Templates: **Event**, **Reminder DM**, **Cancelled DM** and **Waitlist DM**.
- Answers (`ev_rsvps`): pressing the same answer again takes it back. Going past the capacity joins the waitlist in the order people answered; when a Going member changes their answer (or staff raise the capacity) the first in line moves up, gets the attending role and the waitlist DM. With the attending role on, Going members get it and lose it when they change their answer or the event is over (taken back by the sweep even after the module is turned off).
- `/event create` opens a form (title, description, start, length or end, where). Starts are read in the server's time zone by `parseWhen`: `2026-10-20 19:00`, `20 Oct 7pm`, `Oct 20 2026 19:30`, `tomorrow 18:00`, `friday 8pm`, `19:00` (the next one), `in 2h`; 20/10 and 10/20 only when they can't be read the other way round. The length (`parseEnd`) is `2h`, `90 minutes`, `1h 30m`, or an end like `21:00`; an hour when empty. Where matches a voice or stage channel by name or mention, or is kept as text. `/event list`, `/event info <id>`, `/event rsvp <id> <choice>`, `/event cancel <id>` and `/event remind <id>`, with event numbers suggested as people type. Create, cancel and remind are for managers. Every name and description can be changed in Commands; per-server commands are registered with the other modules' in `apps/bot/src/guild-commands.ts`.
- The bot sweeps every minute (`evSweep`): posts events whose post time has come (and any the dashboard job missed), sends the latest reminder that's due once (missed ones aren't sent late; reminders already past when an event is made or moved are skipped), starts events (status `started`, an optional ping mentioning Going members in the channel, Discord's event set active), ends them (status `ended`, final attendance in the message, Discord's event completed, attending roles taken back) and, for repeating events, schedules and posts the next one at the same local time. Ended and cancelled events past the newest 100 are pruned.
- Discord sync (Manage Events): each event is created as one of Discord's scheduled events (a stage or voice channel, or an external place), updated with its details, set active at the start, completed at the end and cancelled with it; deleting an event deletes it. A failure to create one is logged.
- Logs (`ev_log`, the last 500): created, edited, answers, waitlist moves, reminders, starts, ends, cancels, deletes, repeats and failures.

## Temporary voice

- Settings are saved at `/api/v1/servers/:id/temp-voice` (`GET`, `PUT`). The check (`tvIssue` in `packages/core/src/temp-voice.ts`) is shared by the dashboard, the API and the bot: hubs (1 on Free, 10 on Plus; each a voice channel used once, with a category or the hub's own, a name pattern with `{user.name}` and `{count}`, a user limit of 0 to 99, a bitrate from the list and within the server's boost level (96, 128, 256 or 384 kbps), and start locked, hidden or without text chat), the same for rooms made with Create room and `/voice create` (whose category defaults to the one the button or command was used in), the empty-room delay (0 to 60 seconds), rooms per member (1 to 5), the bypass role, remembering members' settings, the panel (channel, template, buttons, labels, posting in rooms) and the command names. A group name another module's turned-on command uses is refused. `GET` also returns the server's voice channels and categories (`GuildView.voice` and `GuildView.categories`), the plan's limits and the boost level.
- Saving queues a `temp-voice` job: the bot registers `/voice` with every module's commands (`apps/bot/src/guild-commands.ts`), checks it has Manage Channels, Manage Roles and Move Members, that the hubs and categories still exist, then posts the control panel or edits it in place (`posted` key `temp-voice-panel`), and takes it down when the module is off or has no panel channel. `POST …/temp-voice/panel` queues `temp-voice-panel` and waits for the bot.
- The panel is a Message Studio template (tagged **Voice panel** in Studio) with Sparko's buttons appended, five to a row (custom ids `tv:<act>`); an embed panel's own buttons and menus have to fit in the rows the buttons leave. Variables (`voice` group): `{room}`, `{room.name}`, `{room.owner}` and `{room.limit}`, filled in when the panel is also posted in each new room's chat.
- The bot needs the GuildVoiceStates intent (not privileged). Joining a hub makes a room (`POST /guilds/:id/channels`, type 2) with the category's overwrites plus Sparko's: @everyone denied Connect when locked, View Channel when hidden, Send Messages without chat; the owner, trusted members, the bypass role and Sparko allowed; blocked members denied Connect. The member is moved in (`PATCH /guilds/:id/members/:user` with `channel_id`). A member who owns as many rooms as allowed (unless they have the bypass role) is moved into their newest one instead. Create room and `/voice create [name] [limit]` reply privately with the link and move the member in only if they're already in voice; a room nobody joins within 60 seconds is deleted.
- Rooms are kept in `tv_rooms` (owner, hub, name, limit, locked, hidden, chat, trusted, blocked, the category's overwrites, members, `waiting`/`open`, when it went empty). Voice state updates keep the member count; an empty room is deleted after the delay by a sweep every 5 seconds (straight away with no delay), even after the module is turned off. On start the bot forgets rooms whose channel is gone, counts members again (so rooms emptied while it was offline are cleaned up), and makes rooms for anyone waiting in a hub. A failed delete is retried 10 minutes later.
- Buttons and `/voice` subcommands (renamable in Commands): create, rename (a form; Discord allows two renames per 10 minutes), limit (a form), lock, unlock, hide, show, trust, untrust, invite (DMs a link and lets them in), kick, block (disconnects them too), unblock, claim (once the owner left the room), transfer (to someone in the room), region and bitrate (menus). Member picks are user menus; untrust, unblock and kick list who's on the list or in the room. They act on the room the panel is in, the room the member is in, or their newest room; only the owner can change it ("Only the room's owner can do this."). Replies are private.
- With "Remember each member's settings" on, a member's chosen name, limit, lock and trusted and blocked lists (25 each) are saved in `tv_prefs` and used for their next room.
- Storage: `GET …/temp-voice/rooms` lists open rooms; `DELETE …/temp-voice/rooms/:channelId` queues `temp-voice-close` and waits for the bot to delete it. `GET …/temp-voice/prefs?q=` lists saved settings; `DELETE …/temp-voice/prefs/:userId` resets one.
- Logs (`tv_log`, the last 500): created, renamed, limit, locked, unlocked, hidden, shown, owner changed (claim or transfer), deleted (empty, by its owner, from the dashboard, or in Discord) and failures.

## Levels & XP

- Settings are saved at `/api/v1/servers/:id/levels` (`GET`, `PUT`). The check (`lvIssue` in `packages/core/src/levels.ts`) is shared by the dashboard, the API and the bot: XP per message (1 to 1,000, the least no more than the most) and its cooldown (0 to 3,600 seconds), voice XP a minute (1 to 100), the curve (gentle, standard or steep), the highest level (1 to 500), no-XP channels and roles, boosts (3 on Free, 25 on Plus; a role or channel used once, 0.1× to 5×), where level-ups are announced (where they chatted, a channel, by DM or nowhere) and every how many levels, reward roles (5 on Free, 50 on Plus; levels within the highest, each level and role once, roles Sparko can give), XP crates (channels, a 0.1% to 25% chance, a 1mi to 1d cooldown, 1 to 100,000 XP, 10 to 600 seconds to open), the three message templates, staff roles and the command names. A name another module's turned-on command uses is refused. `GET` also returns how many members have XP, the crate stats, the plan's `limits`, channels, roles and the log.
- XP for level L to L+1 is a·L² + b·L + c: gentle 3, 30, 75; standard 5, 50, 100; steep 8, 80, 150 (`lvNeed`). Members keep earning past the highest level, for the leaderboard.
- The bot gives XP for each message (`lvOnMessage`): not bots, webhooks, Discord's notices or members with a no-XP role, not in no-XP channels or their threads, and once per cooldown. The amount is random between the least and the most, times the best role boost and the channel's (or its parent's) boost. Every 60 seconds members in voice earn their XP a minute, skipping the AFK channel, members alone (with "Only with company") and muted or deafened members (with "Not while muted"). Members are kept in `lv_members` (XP, messages, voice minutes, name and avatar).
- Reaching a level gives reward roles (`lvRewardPlan`): every one earned, or only the highest, and with "Take rewards back" ones above their level come off after staff take XP or reset. A save that changes the rewards, curve or highest level queues a `levels` job with `rewards: true`, which brings every member with XP in line. Staff changes queue `levels-rewards` for the members touched.
- XP crates: a message that earns XP can drop one, by the chance, in the crate channels (or anywhere XP counts), at most once per cooldown per channel. The crate is the crate template with a green **Open** button (`lv:crate`) added; the first member to press it wins a random amount and the row becomes "name got N XP". Others get "Too slow". Unopened crates are swept every 10 seconds and the row becomes "Nobody opened it in time". Crates are kept in `lv_crates` (the last 200).
- The level-up message, the rank card and the crate are Message Studio templates (tagged **Levels** in Studio); with none picked Sparko uses its Level-up card, Rank card and Crate drop. Variables (`level` flag): `{level}`, `{level.previous}`, `{xp}`, `{xp.next}`, `{xp.left}`, `{rank}`, `{progress.bar}` (▰▱, ten steps), `{progress.percent}`, `{messages}`, `{voice.time}`, `{reward.role}`, `{crate.range}` and `{crate.ends}`, with the usual `{user}` variables. Level-ups in a channel ping only the member who levelled up; DMs never ping.
- `/rank [member]`, `/leaderboard [page]` (10 a page) and, for staff (Manage Server, or the roles in Who can change XP), `/xp give|take|set <member> <amount>` and `/xp reset [member] [everyone]`. Each can be renamed, described or turned off; they're registered with every module's per-server commands. The rank card answers for everyone or only the member.
- Storage: `GET …/levels/leaderboard?q=&page=` (25 a page), `GET …/levels/members/:userId` (XP, level progress, place and reward roles), `GET …/levels/find?q=` (server members, to change XP), `POST …/levels/members/:userId/xp` with `{ mode, amount }` (give, take or set; up to 10,000,000), `POST …/levels/members/:userId/reset`, `POST …/levels/reset`, `GET …/levels/crates` and `POST …/levels/test` with `{ channel, kind }` (a made-up level-up, rank card or crate).
- In the dashboard, Levels & XP has a tab for each part: Settings, Level-up, Reward roles, XP crates, Rank cards, Leaderboard, Logs and Commands. The old XP crates, Reward roles and Rank cards pages lead to their tabs.
- Logs (`lv_log`, the last 500): level-ups, rewards given and removed, XP changes, resets, crates dropped, opened and expired, and failures.
